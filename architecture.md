# Remember — архитектура MVP

Технические решения, принятые на брейнсторме 2026-09-01. Продуктовая плоскость — в `backlog/` (майлстоуны, доки фич, решения).
Этот файл — не продуктовая плоскость: здесь «как строим», а не «что даём человеку».

## Контекст MVP

- Пилот на 10–20 друзей внутри компании — проверить идею. Ничего не масштабируем заранее.
- MVP бесплатный. Монетизации нет. В базе с самого начала ведутся счётчики потребления, чтобы
  позже включить платные тарифы.
- Не в проде, greenfield: скорость важнее осторожности.

## Общая схема

Пять частей:

1. **Мобильное приложение** — Expo / React Native, iOS + Android с первого релиза. Единственный
   клиент. Вход Apple / Google / email-ссылка. При загрузке — доступ к фото-библиотеке телефона,
   кнопка «выбрать всё за дату события». Файлы заливает **напрямую в R2** по подписанной ссылке от
   API. Принимает пуши «ролик готов» и «вас позвали в воспоминание».
2. **API-сервер** — TypeScript. Единственное, с чем общается приложение. Аккаунты, сессии,
   воспоминания, участники, приглашения, проверка прав. Выдаёт подписанные ссылки на загрузку и
   скачивание из R2. Принимает «файл загружен» → создаёт запись о медиа → ставит воркеру задачу.
   Принимает «сделай ролик» → ставит задачу. Ведёт счётчики. Шлёт пуши.
3. **Montage-воркер** — Python. Отдельный процесс, снаружи недоступен. В цикле берёт задачи из
   таблицы `jobs` (`SELECT … FOR UPDATE SKIP LOCKED`). Почти всё время спит.
4. **Postgres** — managed, на том же PaaS. Вся структурированная информация + очередь задач +
   счётчики.
5. **Cloudflare R2** — все файлы: оригиналы, превью, ролики. Приватный бакет, доступ только по
   подписанным ссылкам с коротким TTL.

**Поток:** приложение → API (всё через него, кроме самих файлов) → файлы напрямую в R2 → тяжёлую
работу API перекладывает на воркер через таблицу задач → воркер кладёт результат в R2 и дёргает
API → API шлёт пуш.

## Стек и хостинг

- **Мобильное:** Expo / React Native (TypeScript). `expo-media-library` — подбор по дате,
  `expo-video` — воспроизведение, EAS — сборки, OTA-апдейты. RN/Expo взят по умолчанию; Flutter —
  только если появится опыт в Dart.
- **API:** TypeScript, **Fastify** (решено 2026-09-02: скучный, быстрый, без DI-церемоний NestJS).
- **Воркер:** Python (`ffmpeg`, OpenCV, NIMA в ONNX Runtime на CPU).
- **БД:** Postgres, managed на PaaS. Миграции — **postgrator**, плоские `.sql` в
  `projects/api/migrations`, состояние в `schema_migrations`. Миграции пишутся идемпотентными:
  postgrator шлёт файл и отметку о версии разными запросами, kill между ними переигрывает миграцию.
  Локально база поднимается `docker compose up -d --wait` в `projects/api` — этот compose
  канонический и для api, и для montage.
- **Файлы:** Cloudflare R2 — S3-совместимое API, $0 за исходящий трафик (критично: doc-07 «скачать
  всю галерею» + отдача видео), хранение ~$0.015/ГБ/мес, 10 ГБ бесплатно.
- **Хостинг:** PaaS. Рекомендация — **Railway** (проект с тремя сервисами: API, воркер, Postgres;
  внутренняя сеть между ними; каждый сервис деплоится из своего репозитория по git-push; ~$5/мес
  на этом объёме). Запасной — Render. **Выбор отложен** — на архитектуру не влияет,
  API/воркер/БД переносимы.
- **Репозитории:** polyrepo — отдельный git-репозиторий на каждый сервис (`mobile`, `api`,
  `montage`), подключены сабмодулями под `projects/` в корневом репозитории продукта
  (`remember-product`), где живут `backlog/`, `architecture.md` и конфигурация деплоя. Один репозиторий → один сервис
  на PaaS.
- **Общие типы** между `api` и `mobile` в отдельном пакете не выносим — на объёме пилота проще
  сгенерировать клиентские типы из схемы API либо продублировать нужное.

## Аутентификация

- Провайдеры: **Apple, Google, email magic-link**. Телефон и матчинг контактов — post-MVP.
- Реализация: **своя, по модели данных ниже** + `jose` на проверку провайдерских токенов.
  Решено 2026-09-02, пересматривает прежнюю строку «библиотека (Better Auth или Lucia)»: Lucia
  в 2025 перестала быть библиотекой (депрекейтнута в copy-paste руководство), а Better Auth
  навязывает свою схему и свою модель сессий, которые дерутся с предписанными здесь
  `users` / `auth_identities` / `sessions`, отзываемыми хэшированными токенами и `citext`-ником.
  Своя часть мала: непрозрачный случайный токен в таблице. Единственное, что руками не пишется, —
  проверка подписи Apple/Google, она уходит в `jose`.
- Сессии — таблица с отзываемыми токенами (проще самоподписанных токенов на таком объёме).
  Токен: 32 случайных байта, в базе только SHA-256 хэш, у клиента — сам токен. Транспорт —
  заголовок `Authorization: Bearer` (клиент нативный, куки и CSRF не нужны). У сессии есть срок
  и она отзывается поштучно.
- Magic-link: токен одноразовый, живёт минуты, гасится при использовании. Эндпоинт запроса ссылки
  придушен по частоте — это граница доверия, за ней перечисление адресов и рассылка спама.
  Письмо уходит через **Resend** обычным HTTP-запросом, без SDK: весь протокол — POST с
  Bearer-токеном и JSON-телом (решено 2026-09-04). SES отклонён — SigV4 на каждый вызов и выход
  из песочницы по заявке, много механики на пилот в двадцать человек.
- Apple / Google: доверяем только тому, что проверено — подпись по JWKS провайдера, `iss`, `aud`
  (наш client id), `exp`. Привязка по стабильному `sub` провайдера, **не по email**: email у Apple
  может быть скрытым релеем и может меняться.
- Один пользователь может связать несколько провайдеров (`auth_identities`).
- Ник: уникальный, регистронезависимый (`citext`), меняемый. Внутренние ссылки и приглашения —
  по стабильному `user_id`, **не по нику**. Освобождённый ник свободен для повторного занятия;
  история прежних ников не хранится.

## Модель данных

- **users** — `id`, `username` (уникальный, меняемый), имя, email (Apple может прятать — храним что
  дали), дата создания.
- **auth_identities** — привязки входа: `user_id`, провайдер, стабильный id провайдера.
- **sessions** — `user_id`, хэш токена, срок; отзываемы.
- **email_login_tokens** — токены magic-link: одноразовые, короткий TTL, гасятся в момент обмена.
- **push_tokens** — Expo-токен устройства.
- **memories** — `id`, организатор, название, дата события (начало + опционально конец), счётчики
  `storage_bytes` / `media_count` / `montage_count`.
  Дата события — `timestamptz` с **обязательным** смещением, а не голая дата: doc-02 сверяет это окно
  с моментом съёмки, и голая дата растягивалась бы по таймзоне сервера. Клиент шлёт RFC3339 со
  смещением, `2026-09-02` отвергается `400`. Порядок дат закреплён CHECK-констрейнтом в миграции,
  не только в хендлере — перевёрнутое окно это тихий сбой у doc-02.
- **memory_members** — участник: `user_id`, роль (`organizer` / `contributor` = Добавление /
  `viewer` = Просмотр), кто пригласил. Уникально по (воспоминание, пользователь).
- **invites** — ссылки-приглашения: токен из URL, выдаваемая роль, кто создал, `revoked_at`.
  Многоразовая, без срока; «отозвать» = пометить и сгенерировать новую.
- **contacts** — свой список контактов (m-18, doc-10): `owner_id`, `contact_id` (оба — ссылка
  на `users`, каскад при удалении), `created_at`. Ключ по паре сразу и уникальность, и индекс
  чтения. Односторонняя связь: строка ничего не говорит и не даёт тому, на кого указывает.
- **media_items** — `id`, воспоминание, кто загрузил, тип (photo/video), статус
  (`pending_upload` → `processing` → `ready` / `failed`), ключ оригинала в R2, размер, `captured_at`
  (дата съёмки из EXIF/галереи — для дедупа и порядка в ролике), размеры/длительность, ключи
  `thumbnail` и `preview`.
- **montages** — `id`, воспоминание, кто заказал, статус (`queued` → `processing` → `ready` /
  `failed`), ключ ролика в R2, длительность, `params` (свободный JSON: целевая длина, трек),
  текст ошибки.
- **jobs** — очередь: тип (`media_preview` / `montage`), ссылка на объект, статус, число попыток,
  `run_after` (задержка перед повтором), последняя ошибка.
- **user_usage** — под будущие тарифы: по пользователю суммарно `storage_bytes`, число загрузок,
  число заказанных роликов. Обновляется в той же транзакции, что и запись объекта. Точный
  помесячный учёт / журнал событий — post-MVP.

## Проверка прав (на каждом запросе к воспоминанию)

| Роль          | Может                                                                 |
|---------------|----------------------------------------------------------------------|
| не участник   | ничего                                                              |
| `viewer`      | смотреть галерею и ролики, **скачивать** оригиналы (doc-07)           |
| `contributor` | + загружать медиа, звать людей (поиском и ссылкой)                   |
| `organizer`   | + удалять любое медиа, исключать участников, **заказывать ролик**    |

Своё загруженное медиа может удалить каждый.

## Хранилище и медиа-пайплайн

- **Загрузка:** приложение → API «хочу загрузить (имя, размер, тип, дата съёмки)» → API проверяет
  лимиты, создаёт `media_items` (`pending_upload`), возвращает подписанную ссылку на загрузку в R2
  (multipart, куски 5–10 МБ, докачка при обрыве). Приложение льёт байты прямо в R2, минуя API. По
  завершении → API `processing`, счётчики +, задача `media_preview`.
- **Оригиналы** хранятся как есть, не трогаются (doc-07).
- **Деривативы:** воркер по задаче `media_preview` качает оригинал → фото: `thumbnail`; видео:
  постер + версия 720p H.264 → кладёт в R2 → `media_items.status = ready`.
- **Галерея** показывает деривативы. Оригинал тянется по подписанной ссылке только по явному
  «скачать».
- **Видео в галерее:** прогрессивная отдача 720p-превью. HLS/адаптив — post-MVP.
- **Приватность:** бакет закрытый. TTL подписанных ссылок: загрузка ~1 ч, скачивание ~15 мин.
  Права проверяются при выдаче ссылки.

## Очередь задач

- Таблица `jobs` в Postgres, без Redis. Воркер берёт одну задачу через `FOR UPDATE SKIP LOCKED`.
- Таблицу заводит и владеет ею **montage** (`schema.sql`, `python worker.py init`), не миграции
  api. API в неё только пишет — любое изменение схемы `jobs` идёт через montage.
- Повтор при сбое: `attempts++`, `run_after = now + backoff`; после 3 попыток → `failed`.
- `ponytail:` одна таблица-очередь на одного воркера. Redis / несколько воркеров — только если
  вырастет нагрузка.

## Montage-пайплайн (задача `montage`)

1. **Собрать** все `ready`-медиа воспоминания. Меньше 3 → сразу `failed` («недостаточно материала»).
2. **Скачать** оригиналы из R2 во временную папку.
3. **Нормализовать** `ffmpeg`-ом к общему виду: холст 1080p, H.264, 30 fps, единый звук, паддинг
   под вертикаль/горизонталь. Фото → кадры.
4. **Оценить и отобрать:** семпл кадров (≈1/сек для видео, само фото для фото) → отсев размытых
   (Лаплас) и пере-/недоэкспонированных (гистограмма) → дедуп кадров в пределах ~2 сек по дате
   съёмки → ранжирование по NIMA (ONNX, CPU) → топ до целевой длины (по умолчанию ~60 сек). Отбор
   по оценке, **порядок в ролике — хронологический** по дате съёмки. Нет даты съёмки в файле — для
   порядка берём время загрузки, дедуп по дате пропускаем.
5. **Собрать** `ffmpeg`-ом: клипы обрезаются в 3–5 сек вокруг лучшего момента; фото — 3 сек со slow
   Ken-Burns; кросс-фейд ~0,5 сек между кусками; поверх — один трек из набора 2–3 royalty-free,
   вшитых в воркер, с fade in/out; звук исходных клипов по умолчанию убираем (только музыка). Энкод
   1080p H.264 + AAC, faststart.
6. **Выложить** в R2 → `montages.status = ready` → дёрнуть API → пуш.
7. **Убрать** временные файлы.

Настройки в MVP — только `target_seconds` и `music_track_id` в `params`.

- ✅ **Подход утверждён 2026-09-05** (decision-07): монтируем своим Python-воркером, как описано
  выше; покупной видео-API не берём. Заморозка doc-03 снята.
- ⚠️ **Ceiling:** воркер качает все оригиналы воспоминания на диск. При воспоминании близко к
  потолку объёма это давит на маленький инстанс. Для пилота воспоминание реально <1 ГБ. Апгрейд
  (стриминг / volume) — при необходимости.

## Лимиты (предложены, не утверждены — обсуждаются на ревью спеки)

- Один файл: 1 ГБ или видео ≤ 5 мин.
- На воспоминание: 10 ГБ и 1000 файлов.
- Роликов на воспоминание — без лимита; воркер один, делает их по очереди.
- Значения — в конфиге / env, не в коде, без админки.

## Обработка ошибок

- **Оборванная загрузка** — `media_items` завис в `pending_upload` / `uploading`. Раз в час воркер
  подчищает записи старше 24 ч в этом статусе, освобождает ключ R2 (недособранный multipart —
  abort).
- **Задача воркера упала** — повтор с задержкой, после 3 → `failed`. Превью упало → плейсхолдер +
  «повторить». Ролик упал → у организатора кнопка «повторить».
- **Ссылка протухла** — приложение запрашивает заново.
- **Повторный колбэк «загружено»** — идемпотентно, API смотрит текущий статус.
- **Участника исключили во время его загрузки** — каскад удаления медиа гасит и его задачи в
  очереди.
- **Приложение офлайн при загрузке** — очередь загрузок локально, повтор при возврате в приложение.
- **Воркер убит посреди задачи** — задача остаётся в `running` навсегда, подобрать её некому.
  `ponytail:` в MVP reaper'а нет — воркер один и перезапускается руками. Понадобится, как только
  воркеров станет больше одного или деплой начнёт их перезапускать сам.

## Выход / исключение участника

API удаляет его медиа в этом воспоминании (оригиналы + деривативы из R2), счётчики −, строку
`memory_members` убирает. Уже смонтированные ролики не трогаются, даже если там его кадры (doc-03).

## Пуши

- Expo Push Notifications (бесплатно).
- Два типа в MVP:
  - «ролик готов» — всем участникам воспоминания с токеном (doc-03);
  - «вас позвали в воспоминание» — приглашённому, с deep link прямо на экран загрузки этого
    воспоминания (doc-01, decision-06).
- Напоминание загрузить материал участнику в начальном/промежуточном статусе (doc-06) и напоминание
  о старом воспоминании (doc-05) — тоже в MVP, канал тот же.
- Уведомления о новых загрузках — post-MVP.

## Тесты

По одному живому чеку на нетривиальный кусок, без обвязки сверх `pytest` / `vitest`.

- **API:** интеграционные против реального Postgres. Главное — матрица прав (роль × действие). Плюс
  вход, приём приглашения, срабатывание лимитов, каскад удаления.
- **Воркер:** юнит на логику отбора (оценённые кадры → ожидаемый выбор) на крохотных фикстурах.
  Один e2e: 3 фото + короткий клип → играбельный MP4 примерно нужной длины (`ffprobe` длительность
  в диапазоне, дорожки на месте).
- **Приложение:** для пилота вручную; компонентный тест только на логику «выбрать всё за дату»
  (диапазон + список дат ассетов → ожидаемый предвыбор).

## Вне MVP

- Идентификация по телефону / матчинг контактов.
- Распознавание лиц, «мои фото» (отклонено в `ideas.md`).
- Гостевая веб-загрузка без приложения (отклонено в `ideas.md`).
- Адаптивный стриминг (HLS) — только прогрессивное 720p-превью.
- Богатые настройки ролика (стиль, титры, покадровая правка) — только длина + трек.
- Биллинг / тарифы — только счётчики потребления.
- Передача роли организатора.
- Удаление аккаунта. Когда появится — упрётся в `memories.organizer_id`: воспоминание целиком
  удалять нельзя, значит судьбу воспоминаний ушедшего организатора придётся решать отдельно.
- Удаление воспоминания целиком (уже зафиксировано в doc-01).
- Веб / десктоп-клиент.
- Точный помесячный учёт / журнал событий.
- Масштабирование воркера, Redis, CDN перед R2, модерация контента.

## Перед продом

Осознанно отложено на пилоте, но не забыто. У каждого пункта свой триггер — раньше него делать
нечего, позже него выпускать нельзя.

- **Нет nonce / защиты от повтора на Apple и Google.** id-токен, перехваченный один раз, до
  истечения принимается снова. Триггер: реальные ключи провайдеров.
- **В `app.json` нет `projectId` и EAS-конфига.** Пуш на реальном устройстве не заработает, пока
  не заведён EAS-проект — код отправки написан и сбой обрабатывается, но транспорт не проверен
  ни разу. Триггер: заведение EAS-проекта, вместе с ключами провайдеров.
- **Кнопка входа Apple — не `AppleAuthenticationButton`**, и Google redirect не прописан в
  `app.json`. Первое требует ревью App Store, второе — dev-билда. Триггер: тот же, реальные ключи;
  делается одним куском вместе с ними.

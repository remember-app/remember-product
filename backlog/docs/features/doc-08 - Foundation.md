# Foundation

Три репозитория продукта пусты — в каждом только README от GitLab. Foundation — это скелеты всех
трёх плюс то, чем они друг с другом соединяются: до неё ни одна фича не может начаться, после неё
любая начинается с написания собственно фичи, а не с настройки сборки.

Не фича продукта: человек, открывший приложение, не получает от неё ничего. Она стоит в списке
потому, что организатор велел 2026-09-02 идти пошагово — сначала фундамент всех реп, потом
фундамент продукта (m-3 Accounts), потом фичи.

- Ставится минимум, на котором можно запустить `hello world` в каждом сервисе, прогнать один тест
  и накатить одну миграцию. Всё остальное ставит та фича, которой это понадобится.
- Ни одной продуктовой сущности: ни `users`, ни `memories`, ни экранов. Схема БД целиком приходит
  с фичами, каждая своей миграцией.
- CI, Dockerfile'ы, деплой-конфиг PaaS — не здесь: PaaS ещё не выбран (открытый вопрос
  архитектуры), а до первого зелёного прогона на живом сервисе они не проверяемы.

## projects/api

- TypeScript, **Fastify** (решено 2026-09-02).
- Запускается локально, отвечает на один health-эндпоинт.
- Postgres: подключение из env, инструмент миграций выбран и одна пустая (или служебная) миграция
  накатывается с нуля на чистую базу.
- Локальный Postgres поднимается одной командой (`docker compose` достаточно) — чтобы каждый
  следующий лид не изобретал себе базу.
- `vitest`, один живой тест, проходит.
- Линт/формат — по одному инструменту на задачу, не больше.

## projects/mobile

- Expo / React Native, TypeScript. iOS + Android.
- Запускается в Expo Go / симуляторе и показывает один экран.
- Навигация поставлена и работает хотя бы на двух экранах — иначе каждая фича будет ставить её
  заново и по-своему.
- Обращение к API: базовый URL из env, один вызов health-эндпоинта, видимый на экране. Это и есть
  доказательство, что связка «приложение → API» жива.
- Общий пакет типов с `api` не заводится (решение архитектуры) — типы дублируются или генерируются
  из схемы API.

## projects/montage

- Python. Отдельный процесс, наружу не смотрит.
- Цикл разбора очереди `jobs` из Postgres через `SELECT … FOR UPDATE SKIP LOCKED`: берёт задачу,
  отмечает попытку, при сбое откладывает по `run_after`, после 3 попыток ставит `failed`. Сама
  таблица `jobs` — здесь, она общая для всех типов задач.
- Ни одного обработчика задач: ни `media_preview`, ни `montage`. Регистрируется одна фиктивная
  задача, чтобы доказать, что цикл вертится и повтор работает.
- `ffmpeg`, OpenCV, ONNX — не ставятся: они придут с m-1 и m-2.
- `pytest`, один живой тест на разбор очереди (взял задачу → отметил → упал → повторил → failed).

## Готово, когда

- В каждом из трёх репозиториев `git log` не пуст и в README написано, как это запустить.
- Разработчик с чистой машиной по README поднимает базу, API, приложение и воркер и видит, что они
  соединены: экран приложения показывает ответ API, воркер разбирает свою фиктивную задачу.
- Три коммита ушли в три репозитория, указатели сабмодулей в корневом репозитории обновлены.

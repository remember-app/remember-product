## Implementation Notes

Сервис: projects/api, src/montages/, README «Ролики». Ждёт TASK-192: берёт из него проверку тела заказа и расчёт предела длины — не дублировать.

МАРШРУТ: POST /memories/:memoryId/montages/preview — «сухой заказ». Тело — то же, что у заказа (все поля необязательные). Права те же (только организатор, 403 остальным, 404 не-участнику), проверки те же в том же порядке (списки кадров, треки, длина, порог «мало материала» 409) — потому что предпросмотр, который соглашается на то, что заказ отклонит, хуже отсутствия. Ничего не пишет: ни строки в montages, ни задачи в jobs, ни счётчиков.

ОТВЕТ 200 (числа — по кадрам, которые войдут: готовые за вычетом исключённых этим же телом):
{ "photos": N, "videos": N, "people": N, "min_seconds": N, "max_seconds": N, "target_seconds": N, "orientation": "landscape"|"portrait", "estimate_minutes": N }
- people — число разных загрузивших среди этих кадров (uploaded_by);
- min_seconds / max_seconds — предел из TASK-192;
- target_seconds — то, что заказ записал бы (умолчание 60, зажатое в диапазон, если не названо);
- orientation — названная или landscape;
- estimate_minutes — честная грубая оценка «сколько монтировать»: одна функция в одном месте, формула от числа кадров и длины (ориентир из макета: ~214 кадров и 2:30 → около 15 минут), округление вверх, не меньше 1. Это ориентир, а не обещание, так и записать в README и в комментарии. Веха M-27 считает оценки по этапам журнала — у неё свои; общего кода не делать.

Тесты — по образцу montages.test.ts, в своей тестовой базе; базу remember, очередь, хранилище и процессы человека не трогать. Миграция не нужна; если понадобится — номер выше самого большого на main. Ничего не оставлять кроме результата.

## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Слова человека, doc-12, пункт без черновика: при выключенном интернете экран сначала рисует то,
что есть на устройстве, запросы идут независимо и не блокируют интерфейс.

Сейчас (`frames-material.ts`, `app/memory/[id].tsx`) при входе `items` и `roster` равны null —
ленты нет, стоит либо «Загружаем…», либо баннер с «Повторить». Экран не появляется без ответа
сервера.

**Находка исполнителя, а не догадка:** кэша ответов api в проекте нет вообще, а картинки
кэшируются по переподписываемой ссылке (`tile.tsx:125` без `cacheKey`), и api переподписывает URL
при каждом чтении. Поэтому «просто сохранить список кадров» даст серую ленту из пустых плиток —
это хуже нынешнего «Загружаем…», и человек решит, что приложение сломалось. Кэшировать надо и
записи, и то, что за ними рисуется. У открытого кадра `cacheKey` по id уже есть
(`frame-viewer.tsx:638`) — на него и опереться.

Границы: m-34 и m-36 не трогать, код общий — слить аккуратно, при неразрешимом пересечении прийти
к chief. Плашка — отдельная карточка, здесь не строить. Онбординг — отдельная карточка, здесь не
строить.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Порядок внутри карточки: сначала кэш, потом экран. Если написать «рисуем из кэша», а кэша нет, получится серая лента из пустых плиток — это хуже нынешнего «Загружаем…», и человек решит, что приложение сломали. Кэша ответов api в проекте нет вообще, а картинки кэшируются по переподписываемой ссылке, которую сервер переподписывает при каждом чтении; кэшировать надо и записи, и то, что за ними рисуется. У открытого кадра cacheKey по id уже есть (frame-viewer.tsx:638) — на него и опереться.

Ведущий оценивает объём: это не «показать из кэша», а «завести кэш, которого нет».

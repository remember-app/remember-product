## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Участник заводит лейбл, кладёт в него выбранные кадры пачкой (или заводит лейбл сразу с кадрами), убирает кадры, переименовывает и удаляет лейбл. Кто что может — по временному правилу, пока человек не ответил по decision-12. Кадры от лейблов не страдают.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Завести лейбл: название, цвет, общий или личный; можно сразу с кадрами — лейбл и его кадры появляются вместе или не появляются вовсе. Пустое название или сверх предела — отказ понятным ответом
- [x] #2 Положить в лейбл несколько кадров одним запросом: уже лежащий кадр — не ошибка и не дубль; в пачке кадр другого воспоминания или несуществующий — отказ всей пачки, ничего не положено наполовину. Чужой кадр положить можно — он не становится твоим и прав на него не меняет
- [x] #3 Убрать несколько кадров из лейбла одним запросом; сами кадры остаются в галерее на своих местах
- [x] #4 Переименовать и перекрасить лейбл. Общий ↔ личный после создания не переключается (макет этого не рисует)
- [x] #5 Удалить лейбл: лейбл и его связи уходят, кадры остаются в воспоминании нетронутыми, галерея не меняется
- [x] #6 Права (временное правило по decision-12): общий лейбл переименовывает и удаляет создатель и организатор; класть в общий лейбл может любой, кому можно добавлять; убрать кадр из общего лейбла может создатель лейбла, организатор и тот, кто кадр туда положил; зритель заводит и наполняет только личные, на общих любая запись — отказ «нельзя» тем же ответом, что и у других маршрутов для зрителя
- [x] #7 Чужой личный лейбл на любую запись (положить, убрать, править, удалить) отвечает «не найдено», как будто его нет; хозяин личного лейбла — только он
- [x] #8 Выход участника и исключение: его личные лейблы в этом воспоминании уходят вместе с ним, общие остаются, хозяином становится организатор; кадры живут по своему правилу (кадры ушедшего удаляются и пропадают из всех лейблов, чужие кадры в его лейблах остаются в галерее)
- [x] #9 Всё правило прав — в одном месте кода, помечено как временное по decision-12: когда человек ответит, меняется оно, а не десять маршрутов; те же слова — в README API
- [x] #10 Автотесты снаружи (через HTTP) на каждый пункт выше, включая «удаление лейбла не трогает кадры», «кадр в нескольких лейблах не дублируется в галерее», «положил пачкой и увидел их там»; весь набор api зелёный в своей тестовой базе
- [x] #11 В списке лейблов у каждого лейбла сказано, что спрашивающему можно: править (переименовать, удалить) и класть в него кадры — по тому же правилу прав, что и у записывающих маршрутов, чтобы приложению не повторять правило у себя (экран рисует кнопки правки только там, где сервер разрешил)

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Пять маршрутов записи рядом со списком (src/media/labels.ts): POST /memories/:memoryId/labels (можно сразу с кадрами, одной транзакцией), PATCH и DELETE лейбла, POST и DELETE .../labels/:labelId/media — пачкой, предел пачки равен файловому пределу воспоминания (MEMORY_MAX_FILES, 1000). Всё правило прав — одной функцией labelDenial с пометкой «ВРЕМЕННО, по decision-12»; её же спрашивает список, поэтому у каждого лейбла приходят can_edit и can_add_media (критерий 11) и приложение правило не повторяет. Чужой личный лейбл на любую запись — 404. Выход и исключение: личные лейблы ушедшего удаляются, общие достаются организатору — одним запросом в той же транзакции, что и memory_members (handOverLabels, зовётся из src/memories/members.ts). Кадр соседнего воспоминания, несуществующий и ещё не долетевший — 400 с именами на всю пачку, ничего не кладётся наполовину. Тесты снаружи, через HTTP: 6 новых в src/media/labels.test.ts, весь набор api зелёный (13 файлов, 129 тестов) в своей базе remember_m25 (снесена после прогона).

## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Заказ ролика принимает длину любым числом секунд — от 10 до предела «сумма всех видео + 2,5 с на фото, но не больше 10 минут» — и список треков любой длины с текстом пожеланий. Пустой список — ролик без музыки.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Длина — целое число секунд от 10 до предела воспоминания; предел считается по готовым кадрам за вычетом исключённых этим же заказом; вне диапазона — 400 с числами границ
- [x] #2 Музыка — список: id треков полки и/или ключи своих загруженных треков этого воспоминания, порядок сохраняется; пусто или нет поля — без музыки; неизвестный трек или чужой ключ — 400 с названием
- [x] #3 Текст пожеланий к трекам принимается только вместе с треками (иначе 400), чистится как история ролика

- [x] #5 В params каждого нового заказа список треков пишется всегда, даже пустой
- [x] #6 Автотесты на каждое правило зелёные, README (контракт заказа, переменные окружения) описывает новое

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Спека: doc-03 (пункты от 2026-09-21), макет design/screens/MontageMusic.html, MontageBuild.html. Сервис: projects/api, src/montages/montages.ts и music.ts, README «Ролики».

КОНТРАКТ ЗАКАЗА v2 (POST /memories/:memoryId/montages, все поля необязательные; воркер читает то же — см. TASK на воркере):
- target_seconds: целое. min_seconds = min(10, max_seconds); max_seconds = floor(min(600, Σ длительностей видео + 2.5 × число фото)) по готовым (status=ready) кадрам воспоминания за вычетом exclude_media_ids этого же заказа. Не указано → 60, зажатые в [min, max]. Вне диапазона → 400 {"error":"target_seconds out of range","min_seconds":N,"max_seconds":N}. У видео без длительности считать 0. 10 и 600 — правило продукта, в коде константами; переменные MONTAGE_TARGET_SECONDS_MIN/MAX убрать (MONTAGE_TARGET_SECONDS — умолчание — оставить).
- music_tracks: массив строк, каждая — id полки (bright|warm|calm|night|road) ИЛИ ключ своего готового трека этого воспоминания (music/<uuid>, проверка как у music_track_key сейчас). Порядок сохраняется (это порядок проигрывания). Без повторов (uniqueItems), потолок длины — разумный, 50. Пустой массив или нет поля = без музыки. Неизвестный id / чужой или недогруженный ключ → 400 с названием, как сегодня.
- music_note: строка ≤ 500 знаков, пожелания «как использовать треки». Только вместе с непустым music_tracks, иначе 400 (правило дома: отказывать по имени, а не молча отбрасывать). Чистится и обрезается пробелами как story_text (storable). Пустая после чистки — не пишется.
- Совместимость: пока старое приложение живо, music_track_id и music_track_key продолжают приниматься и записываются как music_tracks из одного элемента; вместе друг с другом (как сейчас) или с music_tracks — 400. Пометить в коде comment «ponytail: убрать, когда приложение перейдёт на music_tracks» — карточка на снятие будет отдельная.
- В params новых заказов music_tracks пишется ВСЕГДА, даже пустой: по нему воркер отличает «без музыки» от строки старого заказа, где поля нет и по умолчанию играл трек «warm».
- Ориентация, история, include/exclude — без изменений.

ВЫНЕСТИ в отдельные функции (их возьмут следующие карточки — итог заказа и шаблоны): расчёт предела длины по воспоминанию и списку исключённых; проверка тела заказа (списки кадров, треки, длина) отдельно от записи. Ни одного маршрута кроме существующего в этой карточке не добавлять.

Миграция не нужна (params — jsonb). Если понадобится — номер выше самого большого на main, никогда между существующими. Тесты идут в своей тестовой базе по README; базу remember, очередь, хранилище и процессы человека не трогать. Ничего не оставлять кроме результата (скрипты, контейнеры, файлы).

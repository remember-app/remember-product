## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Заказ ролика принимает длину любым числом секунд — от 10 до предела «сумма всех видео + 2,5 с на фото, но не больше 10 минут» — и список треков любой длины с текстом пожеланий. Пустой список — ролик без музыки.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Длина — целое число секунд от 10 до предела воспоминания; предел считается по готовым кадрам за вычетом исключённых этим же заказом; вне диапазона — 400 с числами границ
- [x] #2 Музыка — список: id треков полки и/или ключи своих загруженных треков этого воспоминания, порядок сохраняется; пусто или нет поля — без музыки; неизвестный трек или чужой ключ — 400 с названием
- [x] #3 Текст пожеланий к трекам принимается только вместе с треками (иначе 400), чистится как история ролика
- [x] #4 Старые поля одного трека продолжают приниматься и записываются как список из одного; смешать старое с новым нельзя (400)
- [x] #5 В params каждого нового заказа список треков пишется всегда, даже пустой
- [x] #6 Автотесты на каждое правило зелёные, README (контракт заказа, переменные окружения) описывает новое

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Сделано (2026-09-21, коммит 16f9b12, ветка worktree-agent-aadcf0b42153c50c5 в projects/api).

Длина. Предел считается по самому воспоминанию: сумма длительностей готовых видео + 2,5 с на каждое готовое фото, floor(min(600, …)), за вычетом exclude_media_ids этого же заказа; видео без длительности даёт 0. Нижняя граница 10 с, но опускается до верхней, если материала меньше (три фото = ровно 7 с). Не указано — MONTAGE_TARGET_SECONDS (60), зажатое в [min, max]. Вне диапазона — 400 {"error":"target_seconds out of range","min_seconds":N,"max_seconds":N}. 10 и 600 — константы в коде; MONTAGE_TARGET_SECONDS_MIN/MAX убраны из кода, README и .env.example. Схема держит у target_seconds только 'целое' — границы у неё знать неоткуда.

Музыка. music_tracks: массив строк (id полки и/или ключи своих готовых треков этого воспоминания вперемешку), порядок сохраняется как прислали, uniqueItems, maxItems 50, элементы чистятся storable. Пусто или нет поля — без музыки. Неизвестные — 400 {"error":"no such music track","music_tracks":[…]} одним перечнем (пришло на замену старому 'no such uploaded music track'). music_note: <=500 знаков, storable + trim, только вместе с непустым списком, иначе 400 {"error":"music_note needs music_tracks"}; пустой после чистки — не пишется и не отказывает. music_tracks пишется в params ВСЕГДА, в том числе пустым.

Совместимость. music_track_id и music_track_key принимаются и пишутся как music_tracks из одного элемента (в params их больше нет); любые два способа назвать музыку в одном теле — 400 {"error":"the music is named more than one way","fields":[…]} (заменило 'mutually exclusive'). В коде оба помечены ponytail-комментарием.

Вынесено. materialLeft(memoryId, exclude) — один запрос, отдаёт {ready, min_seconds, max_seconds}; checkOrder(memoryId, body) — вся проверка тела (кадры, треки, пожелание, длина) отдельно от записи, отдаёт либо params, либо {code, body}. Обе экспортированы для TASK-197 и TASK-198. Маршрутов не добавлено, миграций нет.

Тесты: npx vitest run — 10 файлов, 101 тест, всё зелёное; своя база remember_task192 и свой временный MinIO, оба удалены после прогона. tsc --noEmit чисто, biome чисто по изменённым файлам. Новые/переписанные тесты: предел длины по материалу (фото, видео, неизмеренное видео, вычет исключённого, потолок 10 минут), зажим умолчания, список треков и его порядок, пустой список, старые поля, смешение способов, пожелание без треков, чистка ключа и пожелания.

Замечено сверх задачи (не трогал): мобильное приложение читает params.music_track_id / music_track_key в списке роликов (src/memory/films.tsx) и шлёт target_seconds 120 — у новых заказов музыки в этих полях не будет, а длина может не влезть в предел; в src/memories/memories.test.ts на main есть расхождение форматирования с biome.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Причина найдена и подтверждена по исходникам платформы (коммит 462250f + мерж 3ecf2f7 + правка ревью f29d5e6, все в mobile/dev): src/lib/upload/send.ts открывала оригинал из галереи (readPart → source.open()) без режима — по умолчанию ReadWrite, а файл галереи телефон даёт только на чтение. Из-за этого не проходила ни одна загрузка с настоящего устройства с самого начала, включая свежие локальные снимки — iCloud (TASK-419) была не при чём, до её кода дело не доходило. Правка: source.open(FileMode.ReadOnly). Симулятор и моки это никогда не ловили (не воспроизводят запрет записи в песочнице) — тестовая подмена файловой системы переписана так, чтобы держать контракт платформы.
Заодно (по требованию chief): у причин unreadable/iCloud появилось поле detail (шаг + дословный ответ телефона) — видно в скобках на экране и уходит в лог api лёгким GET /health?upload_failure=... (без правок в api, без ожидания ответа, раз на файл+причину за запуск).
Ревью подтвердило: эффект настоящий (iOS и Android), подмена в тестах не для вида, отчёт на /health не течёт секретами и не бьёт по частоте, моё разрешение конфликта с TASK-426 (parkedReason вместо устаревшей parkedLines) чистое. Вердикт ревью — публиковать обновением по воздуху можно. Полный прогон (123/2147) и tsc чистые.
Не проверено на реальном устройстве (не может быть проверено без него) — подтвердит первая попытка человека после обновления; если не поможет, причина будет видна в скобках на экране и по upload_failure в логе api.

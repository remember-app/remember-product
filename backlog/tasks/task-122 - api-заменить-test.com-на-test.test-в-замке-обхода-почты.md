## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Человек 2026-09-09: домен обхода письма без ключей (TASK-115) сменить с test.com на test.test. Причина — ревью нашло: test.com настоящий зарегистрированный домен, которым продукт не владеет, и однажды на нём может появиться почта; test.test — из зарезервированного навсегда диапазона (RFC 2606, .test/.example/.invalid), никогда и никем не регистрируется. Заменить домен во всех местах: projects/api/src/auth/plugin.ts (сама проверка и комментарии рядом — их обоснование тоже стоит поправить под новую причину выбора домена), projects/api/src/auth/config.ts, projects/api/src/auth/testing.ts, projects/api/src/auth/auth.test.ts (включая матрицу и evil.test.com → evil.test.test), README и .env.example в api и mobile.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Домен обхода письма переведён с test.com на test.test везде.

api (коммит 1032b9e, ветка агента agent-a8b367ebc2f8d2379):
- src/auth/plugin.ts — сама проверка (endsWith на «@test.test») и комментарии вокруг неё; обоснование выбора домена переписано: раньше оно держалось на «письмо туда всё равно никуда не уйдёт», теперь — на том, что зона .test зарезервирована RFC 2606 навсегда, её нельзя зарегистрировать и почтового сервера там не будет ни у кого. Отдельно названо, почему домен «вроде бы ничей» не годится: на нём может завестись ящик, и ссылка входа уедет владельцу.
- src/auth/config.ts, src/auth/testing.ts — упоминания в комментариях.
- src/auth/auth.test.ts — вся матрица: фикстура doorEmail(), имя и текст теста двери, подделка evil.test.com → evil.test.test (проверка, что совпадение идёт по целому хвосту «@test.test», а не по суффиксу).
- README.md и .env.example — все примеры, таблица переменных, curl-фрагменты; в описание добавлена причина выбора домена.

mobile: projects/mobile/README.md — раздел про ссылку входа в разработке и curl-пример (you@test.com → you@test.test). Правка сделана, НО НЕ ЗАКОММИЧЕНА: агент запущен в изолированном worktree репозитория api, и git-операции вне этого worktree блокируются средой. Изменение лежит в рабочей копии mobile и ждёт коммита от того, кто не изолирован.

Тесты: полный набор api зелёный — 8 файлов, 80 тестов, три прогона подряд. Прогонять пришлось на отдельной базе: на общей локальной базе живой воркер montage (worker.py run, запущен в среде) разбирает задания, которые создаёт montages.test.ts, и переводит их из queued в running прямо посреди проверок — 5 тестов монтажа падают по этой причине, к правке домена отношения не имеют (подтверждено логом воркера: он забирает те самые job id в минуту прогона). На изолированной базе тех же тестов — зелено.

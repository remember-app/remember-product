## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Проверка Apple для внешней группы TestFlight требует рабочего входа, а у нас вход только по коду из письма. Человек 2026-09-25 выбрал завести одну учётку рецензента с постоянным кодом. Дверь узкая: один заранее названный адрес, всё остальное как обычно.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Постоянный код входа работает ровно для ОДНОГО адреса, заданного настройкой; для любого другого адреса (включая похожие: другой регистр, адрес с плюсом, другой домен, лишние пробелы) код по-прежнему случайный и приходит письмом — существующие тесты входа по коду и замка «в боевом режиме обхода почты нет» (m-15) остаются зелёными и не отменяются
- [ ] #2 Дверь включается и выключается ОДНОЙ настройкой (например REVIEW_LOGIN одной строкой «адрес:код»); не задана или пуста — двери нет вовсе, и это закреплено тестом; есть тест, который краснеет, если дверь откроется шире: соседний адрес, тот же адрес с другим регистром или плюсом, любой другой код, пустая или битая настройка, включённая только половина настройки
- [ ] #3 Ограничения частоты и попыток на этот адрес работают как у всех (дверь не обходит защиту от подбора); вход этим путём создаёт обычную сессию, письмо не отправляется; дверь не зависит от режима разработки (EMAIL_LOGIN_DEV_BYPASS) и работает в боевом режиме только если настройка задана
- [ ] #4 Ни адрес, ни код не попадают в репозиторий продукта (значения только в окружении) и в логи (строки логов входа этим путём не содержат ни адреса, ни кода — закреплено тестом); значения кладутся туда, где лежат остальные секреты инфраструктуры; docs/auth.md и docs/running.md описывают дверь как осознанное узкое исключение, без значений
<!-- AC:END -->

## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
На dev api красный: в projects/api/src/montages/montages.test.ts падают от трёх до пяти проверок, и число прыгает от прогона к прогону при одном и том же порядке. Пять прогонов подряд одного файла: 5, 4, 4, 3, 4 красных. То есть это не «сломано», а мигает.

Причина найдена и проверена по коду. Список роликов читается как order by m.created_at desc, m.id desc (projects/api/src/montages/montages.ts:193). created_at — это now(), то есть время транзакции, а не время вставки: четыре заказа, поставленные подряд в одном тесте, получают один и тот же created_at с точностью до микросекунды. Дальше порядок решает m.id desc, а id в таблице — DEFAULT gen_random_uuid(), то есть случайный. Получается, что при равенстве created_at строки встают в случайном порядке, и проверка, ждущая «новые сверху», падает тогда, когда случай совпал.

Это чужое красное, к m-37 оно не относится: карточки этапа трогают projects/mobile. Но карточка не закрывается, пока на общем dev красное, и пока это мигает — прогон api ничего не доказывает.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Найдено ведущим этапа m-37 при сверке dev, 2026-10-04. Пять прогонов одного файла подряд: 4, 3, 4 красных (и 5, 4 на полном наборе). Пункты: projects/api/migrations/020.do.montages.sql — created_at timestamptz NOT NULL DEFAULT now(), id uuid DEFAULT gen_random_uuid(); projects/api/src/montages/montages.ts:193 — order by m.created_at desc, m.id desc.

Чинить надо упорядочивание, а не проверку: список «новые сверху» обещает смысл, и он сейчас не выражен ничем, кроме случайности. Варианты, которые стоит рассмотреть: счётчик порядка в таблице рядом с created_at (тогда порядок выражен данными и не зависит ни от часов, ни от uuid), либо сортировка по jobs — заказ кладёт туда строку в той же транзакции.

Правку делать не в этом прогоне, а отдельной карточкой: api трогает другая работа. Здесь только граница и причина.

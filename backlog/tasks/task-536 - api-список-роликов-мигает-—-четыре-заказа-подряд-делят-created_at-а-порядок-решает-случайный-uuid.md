## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
На dev api красный и мигает: от трёх до девяти проверок за прогон, число прыгает от прогона к прогону при одном и том же порядке.

**Причина оказалась не в сортировке.** Исходное объяснение «порядок по created_at, где время — это время
транзакции, а равные значения разбирает случайный id» оказалось неверным: запрос уже читает
`order by m.created_at desc, m.id desc`, id — первичный ключ, то есть порядок уже тотальный.
Замер: четыре строки в одной транзакции делят одно время, порядок возвращается одинаковый каждый
раз. Первое же измерение типов тянет на 199 из 200 «равных» — это артефакт усечения до миллисекунд,
а не совпадение; в полной точности совпадений ноль из ста.

**Настоящая причина: жив��й обработчик работает на той же базе, что и проверки.** Он забирает задачи,
которые пишут проверки: в окне прогона видно, как строки теста уезжают из `queued` в `running` и
`done`, а ролики из `queued` в `processing`. Сервер сам никогда не помечает задачу выполненной — это
делает только обработчик, — поэтому проверка и видит `running` вместо `queued`. Все падения — это
подмена состояний и числа этапов, ни одно не про порядок.

Связано с настройкой: в `projects/api/.env` стоит `DATABASE_URL=postgres://...@5432/remember` — та
же база, что у стенда, — а проверки подхватывают её через `--env-file-if-exists=.env`. В корневом
Makefile рядом уже есть `TEST_DATABASE_URL ?= $(DATABASE_URL)_test`, то есть база для проверок
объявлена, но набор её не использует.

Что сделать: чтобы проверки сервера ходили в `TEST_DATABASE_URL`, а не в стендовую базу. Стенд при
этом продолжает работать, и прогон api перестаёт зависеть от того, запущен ли обработчик.

Побочно, из того же разбора: проверки роликов считают очередь общей и опираются на то, что рядом
никто не накидал задач. Это отдельная забота, здесь не трогать.

Проверить: с живым обработчиком полный набор api несколько раз подряд даёт одно и то же число
красных — ноль.

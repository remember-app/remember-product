## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Сейчас воркер после пустой очереди спит 5 секунд и лишь потом смотрит снова — каждое превью после загрузки и каждый заказ ролика ждут этой паузы на ровном месте. Postgres, который и так держит очередь, умеет разбудить воркер сам через уведомление по каналу, в момент, когда задача поставлена. Редкий опрос остаётся как запасной путь — пропущенное уведомление не должно оставлять задачу висеть.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Таблицу jobs заводит и владеет ею montage (schema.sql), api только пишет в неё — поэтому будильник ставится там же, а не правками в api. Предлагаемый путь: AFTER INSERT-триггер на jobs, вызывающий pg_notify('jobs', '') — идемпотентно определённый (CREATE OR REPLACE FUNCTION + DROP TRIGGER IF EXISTS/CREATE TRIGGER), в стиле остального schema.sql, переигрывается на каждом worker.py init. Это же покрывает и ручной enqueue() из CLI, без отдельного вызова pg_notify там.

В worker.py: LISTEN jobs один раз в начале run(). На пустой очереди вместо time.sleep(IDLE_SLEEP_SECONDS) — ожидание на conn.notifies(timeout=...) (psycopg 3.2, уже в requirements.txt): просыпается по первому уведомлению или по таймауту, что раньше. Таймаут — запасной опрос, сделать его заметно реже (например 30 секунд вместо 5). run_once(), ретраи, backoff, sweep — не трогать.

Тест: вторая коннекция делает LISTEN jobs, затем на первой — worker.enqueue(...); ассерт, что вторая получает уведомление через conn.notifies(timeout=...), а не через полный интервал опроса. Это тестирует триггер и будильник напрямую, без запуска бесконечного run().

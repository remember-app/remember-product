## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Ссылка входа по email уходит настоящим письмом через почтового провайдера вместо строчки в логе сервера. Без ключей провайдера сервис по-прежнему поднимается и внятно отвечает, что почта не настроена, вместо падения.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 POST /auth/email/start шлёт письмо со ссылкой входа через почтового провайдера вместо записи в лог; сама ссылка и токен нигде в логах больше не появляются
- [x] #2 Без ключей почтового провайдера в env сервис поднимается штатно, а POST /auth/email/start отвечает 503 {"error":"mail not configured"}, не падая и не пятисотя
- [x] #3 Отказ провайдера при реальной отправке (сеть/API вернули ошибку) не отвечает 200 и не путается с «адрес не существует» — свой код ответа, ничего секретного в теле
- [x] #4 Переменные окружения почтового провайдера названы по образцу существующих (как у R2), перечислены в api/.env.example с комментарием
- [x] #5 api/README.md описывает ответ 503 и переменные окружения почты
- [x] #6 Существующие тесты пакета, входящие в сессию через email, не ломаются без реальных почтовых ключей — новых тестов на доставку письма специально не пишем, это отдельным ходом
<!-- AC:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Смотри src/auth/plugin.ts — комментарий ponytail в /auth/email/start ровно на месте выпуска ссылки (сейчас request.log.info с link), и src/auth/email.ts. Прецеденты в этом же репозитории: src/media/r2.ts storageConfigured()/503 «storage not configured» — тот же приём для «не настроено»; src/memories/push.ts EXPO_PUSH_URL — тот же приём переопределяемого через env адреса, чтобы тесты не били по реальной сети. Провайдер выбран лидом: Resend — обычный HTTP POST с Bearer-токеном и JSON-телом, без SDK и подписи запроса (AWS SES отклонён: требует SigV4-подпись и в песочнице шлёт только на заранее подтверждённые адреса — тяжело для пилота на 10-20 друзей). Предлагаемые имена: RESEND_API_KEY, MAIL_FROM — отдельный неймспейс MAIL_* от EMAIL_LOGIN_* (тот управляет TTL/частотой токена, не доставкой). src/auth/testing.ts сейчас достаёт токен из лога (linkToken) — это используют signIn() и несколько других тестовых файлов пакета (upload/gallery/members/memories) только чтобы получить сессию, самой доставки письма они не проверяют. Раз лог токен больше не несёт, testing.ts стоит переключить на прямой вызов startEmailLogin() из email.ts (он уже экспортирован) для минтинга токена в тестах — тогда остальной пакет не зависит от почты вовсе, а свои тесты доставки в auth.test.ts проверяют /auth/email/start отдельно с застабленным исходящим вызовом. architecture.md (корень, не трогать в этой задаче — она в другом репозитории) содержит пункт «Перед продом» про токен в логе с триггером «подключение почтовика» — эта веха и есть триггер, снимает его следующая задача в root-репозитории. Зона этой вехи — src/auth/**; НЕ трогать src/media/**, src/memories/** — там параллельно работают другие лиды (m-5 Gallery download, m-6 Contribution status). Перед коммитом подтяни main — если конфликт в чужом файле, не правь вслепую, сообщи лиду.

Решение чифа 2026-09-04: на время параллельной работы трёх вех конвейер сокращён до кода — ревью и тестирование (авто и ручное) не запускаются, веха не закрывается. Новых тестов специально не заводить; ломать существующие нельзя.

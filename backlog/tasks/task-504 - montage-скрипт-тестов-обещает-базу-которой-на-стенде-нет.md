## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Инструкция в карточке TASK-500 — «`cd ../api && docker compose up -d --wait`, затем
`./test-in-docker.sh`» — на текущем стенде неисполнима.

Причина: `./test-in-docker.sh` жёстко указывает на базу `remember_test`, а в ней применены
миграции только до 180. Миграция 190 (комментарии к кадру, TASK-497) там не накатана, и любой прогон
этим скриптом падает на `relation "frame_comments" does not exist`. Проверено при приёмке TASK-500:
миграцию накатали, после неё полный набор зелёный (533 теста).

Это не разовая беда TASK-500. Тот же корень уже стоил двух ведущих за ночь, с двух сторон: один
сравнивал схемы двух баз и получил «not comparable», другой получил «нет такой таблицы» вместо
результата. Скрипт предполагает базу, у которой есть все миграции, — и на стенде её нет.

**Что делать.** Скрипт сам должен приводить свою базу в порядок, а не предполагать, что это сделал
кто-то: накатывать перед прогоном недостающие миграции api (тем же `npm run migrate`, но против
`remember_test`) — либо честно падать с сообщением, в котором написано, что база не накатана и
какой командой это лечится. Второе дешевле и понятнее; первое удобнее и снимает вопрос целиком.

Побочная причина, которую стоит учесть: общая `remember_test` — общая беговая площадка. Соседний
исполнитель по вехе работает в том же репозитории и чистит общие таблицы, поэтому общая база —
источник взаимных сбоев. Если делать первые миграции, подумать, не нужна ли задаче своя база, как
это сделал исполнитель TASK-500.

Правило, которое здесь действует: инструкция не должна обещать то, чего нет. Пока обещает, каждый
следующий исполнитель будет наступать, и каждый раз это будет стоить времени тому, кто его читает.

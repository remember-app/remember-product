## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Ветка montage: task-158-media-screening, коммит e1c02fb. Тесты воркера целиком зелёные (82 passed).

Что сделано:
- Новый тип задачи очереди media_screening (screening.py) — по id media_items качает оригинал и зовёт selection.judge, ответ пишет в screening_rejected/screening_reason (миграция api 060). false, а не null, для кадра, который анализ посмотрел и оставил.
- Задача ставится в конце media.media_preview, ровно в момент перехода строки в ready (media.py пишет INSERT в jobs руками: worker импортирует media, обратно импортировать нельзя).
- Докатка: worker.sweep_media_without_screening — ready + пустой screening_rejected, без уже идущей задачи и без недавно сдавшейся; тот же CATCH_UP_AFTER_HOURS и та же форма запроса, что у sweep_photos_without_previews (положена рядом с ней и по той же причине: обе берут константу из worker.py).
- README montage: раздел «Предложение отсева (media_screening)» — контракт колонок, докатка, оговорки.
- test_screening.py, 6 живых проверок: ready-медиа получает предложение без заказа ролика; забракованный кадр называет причину; нечитаемый файл получает unreadable и задача завершается done (а не бесконечное «не посчитано»); докатка старого материала и её неповторение; отсутствующий в бакете оригинал оставляет колонки null и повторяется только через сутки; заказ ролика не меняется, когда весь материал помечен забракованным.

Технические решения:
1. duplicate из per-item предложения исключён сознательно. Дедуп в selection сравнивает кадры между собой (серия в пределах двух секунд, остаётся самый резкий) — по одному файлу такой вердикт не выносится, а вердикт, опирающийся на соседей, переворачивался бы при каждой новой загрузке того же мгновения, и для «самый резкий» нужна колонка с оценкой, которой в media_items нет. Пишутся три причины, верные о самом файле: unreadable, blur, exposure. Дедуп остаётся в choose при заказе — там организатор его и видит. Если бурст-предложение понадобится, это отдельная задача: нужна хранимая пооценка кадра (колонка в api) и пересчёт бурста при каждой новой загрузке.
2. Оценивается оригинал, не превью: 720p-перекодировка сглаживает края, по которым меряется резкость, и предложение разошлось бы с тем, что скажет сам заказ.
3. Недоступное хранилище не пишет «брак»: обычные повторы очереди, после третьей попытки колонки остаются null, докатка пробует через сутки. Статус media_items задача не трогает ни при каком исходе — забракованный кадр остаётся в галерее и скачивается.
4. Обработчик вынесен в свой модуль screening.py, а не в media.py: media.py не может импортировать selection (selection импортирует media — цикл). Развилка ready-задач в worker.py — HANDLERS и SWEEPS по строчке.

Оставлено вне задачи: README api описывает причину примером blurry, воркер пишет blur (CHECK на колонке нет, api текст просто отдаёт) — расхождение в чужом репозитории, не трогал.

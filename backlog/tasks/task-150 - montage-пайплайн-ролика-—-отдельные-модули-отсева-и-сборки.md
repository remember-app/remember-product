## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Сейчас весь монтаж — один модуль montage.py: отсев брака, выбор лучших моментов и склейка ffmpeg-ом перемешаны в одних функциях. Спека doc-03 требует, чтобы сервис монтажа состоял из заменяемых модулей — отсев, понимание, режиссёр, ритм, сборка, — каждый из которых можно заменить, не трогая остальные. Эта задача — только про отсев и сборку; понимание, режиссёр и ритм — отдельные задачи этой вехи (m-23), которые лягут в эти же швы.

Разнести текущий код montage.py на:
- модуль отсева: _grey_frames, _sharpness, _exposed, _best_moment, _dedup, choose — всё, что решает, какие куски войдут в ролик и в каком порядке. Пусть возвращает не только выбранное, но и отклонённое — с причиной (резкость/экспозиция/дубль) на каждый отклонённый кусок: это то, что понадобится следующей задаче (предложение об отсеве до заказа).
- модуль сборки: _normalise, _assemble и всё, что кладёт куски на холст и режет ffmpeg-ом. Он принимает готовый список кусков (с длительностью и местом в ролике) и ничего не знает о том, как они были отобраны — ни про резкость, ни про нейросеть.
- оркестратор (может остаться в montage.py) вызывает модули по очереди, как сейчас.

Дополнительно: организатор может отметить кадры «включить» и «исключить» ещё до сборки (doc-03, Components). Контракт, зафиксированный для всей вехи m-23 (в т.ч. для api-задачи «заказ ролика принимает историю, выбор кадров и свой трек»): montages.params.include_media_ids и montages.params.exclude_media_ids — необязательные списки id из media_items. Отбор должен это уважать уже сейчас, в сегодняшнем алгоритме, независимо от того, есть ли план от нейросети-режиссёра (появится отдельной задачей и будет обязан соблюдать то же правило): «исключить» никогда не попадает в ролик, даже если алгоритм считал бы его лучшим; «включить» попадает всегда, если файл технически пригоден (читается, есть кадр), и не считается частью бюджета target_seconds — отбор остальных подстраивается под оставшееся время.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Разнесено на три файла в projects/montage:

- selection.py (отсев) — Piece, _grey_frames, _sharpness, _exposed, _best_moment, _dedup, judge, choose. judge смотрит один скачанный файл: читается ли, есть ли годный кадр, где лучший момент. choose из оценённых кусков выбирает те, из которых выйдет ролик. Оба возвращают и отклонённое: на каждом куске поле rejected с кодом причины — unreadable, blur, exposure, duplicate, excluded, no_room. Коды, а не фразы: их будет читать код (TASK-158) и локализовать приложение.
- assembly.py (сборка) — CANVASES, TRACKS, CROSSFADE_SECONDS, length_of, _normalise, _assemble и один вход assemble(): нормализует каждый кусок на холст, меряет реальную длину, склеивает xfade-ом и кладёт трек сверху. Про резкость, экспозицию и дубли не знает ничего; Piece не импортирует — контракт на утиной типизации (path, kind, seconds, start).
- montage.py (оркестратор) — читает заказ, качает оригиналы, зовёт selection.judge на каждый файл, selection.choose на все оценённые, assembly.assemble на выбранные, режет обложку, пишет строку и стучится в API.

Направление зависимостей: montage -> selection, assembly; selection -> assembly только за length_of (бюджет отбора меряется длиной СОБРАННОГО ролика, а кросс-фейды принадлежат сборке). Обратной зависимости нет.

include_media_ids / exclude_media_ids из params уважаются в selection.choose — единственном месте, так что будущий план от нейросети-режиссёра обойти их не сможет. Исключённое не в ролике никогда; включённое в ролике всегда, если файл читается и в нём есть кадр (blur и exposure этим перебиваются, unreadable — нет: это не мнение, а отсутствие картинки). Время под включённые тратится первым, остальной отбор подстраивается под остаток target_seconds. Названное в обоих списках сразу остаётся за бортом. Дедуп: если в серии есть включённый кадр, за серию стоит он, а не самый резкий. Сравнение id нормализуется через str() — из json приходят строки, из Postgres uuid (на это есть тест).

Два решения, принятых по ходу (в задаче их не было):
1. Пустой отбор (организатор исключил вообще всё) — отказ без повторов с человеческим текстом вместо падения _assemble на пустом списке. Пятый отказ такого рода, README обновлён.
2. Порог MIN_ITEMS остался там же, где был — на оценённых кусках ДО применения исключений. Значит заказ, где исключено всё кроме двух кадров, соберёт короткий ролик из двух, а не откажет. Поведение роликов без include/exclude не тронуто; ужесточать порог без спроса не стал.

Тесты: полный набор против живых Postgres, MinIO и ffmpeg — 61 passed (было 46). Чистый отсев переехал из первой половины test_montage.py в test_selection.py (ни базы, ни ffmpeg): туда добавлены проверки причин отклонения и все правила include/exclude. В живые тесты добавлены два e2e-ролика: с exclude кусков становится меньше, с include в ролик входит забракованное алгоритмом фото. Гонялось в своей базе remember_task150 (создана, миграции API накатаны, после прогона удалена), бакет — локальный MinIO стенда.

## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Обработчик ведёт журнал сборки ролика по пяти этапам, пока собирает: что отсеял и почему, что взял, что осталось. Журнал пишется и без нейросети — по решениям собственного отбора — и попадает в базу сразу, а не пачкой в конце.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 С первой секунды сборки у ролика заведены пять этапов с оценкой времени; по ходу каждый переходит из ожидания в работу и в готово, оценка «осталось» уточняется, у готового записано, сколько он занял; при падении идущий этап помечен упавшим
- [ ] #2 Отсев: на каждый отсеянный файл есть запись с решением «мимо» и причиной (смазан, экспозиция, не читается…); у этапа итог «годятся N из M»
- [ ] #3 Разбор кадров: у файла с сохранённым описанием есть запись с меткой «что увидел» (описание и кто на кадре); у этапа итог «описано N из M»; описаний нет — этап проходит и честно говорит «0 из M»
- [ ] #4 Режиссёрский этап без нейросети: по каждому файлу решение «беру» или «мимо» с причиной; серия одинаковых кадров — одной записью «взял 1 из N»; «включить» и «исключить» организатора видны в решениях
- [ ] #5 Ритм и склейка: у этапа ритма запись, под какой трек и темп подогнаны куски; у склейки видно прогресс по кускам и итог — сколько склеек и какая длина
- [ ] #6 Записи попадают в базу по мере появления, а не пачкой в конце этапа или сборки: тест читает журнал из другого соединения посреди сборки и видит уже написанное
- [ ] #7 Повторная попытка того же ролика (повтор задачи или «повторить») начинает журнал с чистого листа; сбой записи журнала не роняет сборку
- [ ] #8 Автотесты воркера на записанных ответах зелёные, в сеть и в базу человека не ходили; README воркера описывает, что и когда пишется в журнал
<!-- AC:END -->

ПОРЯДОК И ЗАВИСИМОСТИ. ЭТАПЫ (ключи как в TASK-200): screening, understanding, directing, rhythm, assembly. Пайплайн уже раскладывается на них: judge по каждому файлу в montage.py → чтение сохранённых описаний (media_understandings) → director.direct, а без модели selection.choose → rhythm.fit → assembly.assemble.

ЧТО ПИСАТЬ. Новый файл journal.py — тонкий писатель (открыть этапы, добавить запись, обновить счётчики/оценку, закрыть этап), остальные модули остаются независимыми: пишет оркестратор montage.py по тому, что модули вернули (решения и причины у selection уже есть — коды unreadable/blur/exposure/duplicate/excluded/no_room; выдернуть из _dedup размер серии для «взял 1 из N» — правка минимальная). Записи только кодами и данными, без готовых русских фраз (слова показывает приложение); исключение — мысль модели, её пишет TASK «режиссёр-нейросеть пишет мысли», не эта.
- screening: запись на каждый отсеянный файл (решение «мимо» + причина); итог этапа: годятся N из M.
- understanding: по каждому файлу с сохранённым описанием — запись с меткой «что увидел» (описание, кто на кадре); итог: описано N из M, число лиц/людей. Описаний нет — этап проходит, итог честно «0 из M».
- directing (путь без модели): по каждому файлу «беру» или «мимо» с причиной; серия одинаковых кадров — одна запись «взял 1 из N»; «включить»/«исключить» организатора видны в причинах. Обзорной мысли у алгоритма нет — не придумывать.
- rhythm: одна запись — под какой трек и какой темп подогнаны куски (и сколько кусков сдвинуто); итог этапа.
- assembly: прогресс по кускам (сделано N из M) по мере склейки; итог: сколько склеек, какая длина.
ОЦЕНКА ВРЕМЕНИ: в начале сборки заведены все пять этапов с оценкой (по числу файлов, заказанной длине и т.п. — константы «на глаз» вынести в одно место как ручку для подстройки по реальным прогонам); идущий этап пересчитывает «осталось» по факту; у завершённого записано, сколько занял. Согласовать формулу и числа с оценкой «соберём за N минут» в api (TASK-197, README api), чтобы обещание на итоге заказа и «осталось ≈» на монтаже не расходились.
ЖИВОСТЬ: запись — сразу отдельной командой на своём соединении с автокоммитом (или иначе так, чтобы читающий api видел её до конца этапа) — иначе «в прямом эфире» превращается в «пачкой в конце». Проверить тестом, который читает журнал из ДРУГОГО соединения посреди сборки.
ПОВТОР: новая попытка того же ролика (ретрай задачи, «повторить» упавшего) начинает журнал с чистого листа — старые записи и этапы удаляются в начале прогона.
ПАДЕНИЕ: упавший ролик оставляет журнал как есть, идущий этап помечен упавшим.
Сбой записи журнала не должен ронять сборку ролика (журнал — зрелище, не суть): предупреждение в лог, сборка идёт дальше.

ТЕСТЫ И СТЕНД. У человека поднят живой стенд, его база remember, очередь, MinIO и процессы — не трогать. Тесты воркера чистят jobs и пишут в бакет: гонять только в своей базе (создать remember_m27_test на localhost:5432, postgres/postgres; миграции api накатить туда: `cd projects/api && DATABASE_URL=… npm run migrate` из main api) и в своём бакете (создать, например, remember-m27-test в локальном MinIO; бакет remember не трогать: R2_BUCKET=remember-m27-test). Запускать с AI_PROVIDER/GEMINI_API_KEY/OPENAI_API_KEY сброшенными (`env -u AI_PROVIDER -u GEMINI_API_KEY -u OPENAI_API_KEY …`): в .env воркера стоит живой поставщик, тесты идут только на записанных ответах и в сеть ходить не должны. По окончании удалить свою базу и бакет. Ни одного живого вызова нейросети.
ГИТ: коммит в ветку worktree, перед сдачей подтянуть свежий main montage (rebase) и прогнать тесты снова; в main сливает лид.

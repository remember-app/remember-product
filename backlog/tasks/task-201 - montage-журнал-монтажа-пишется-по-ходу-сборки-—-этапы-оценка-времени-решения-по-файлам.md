## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Обработчик ведёт журнал сборки ролика по пяти этапам, пока собирает: что отсеял и почему, что взял, что осталось. Журнал пишется и без нейросети — по решениям собственного отбора — и попадает в базу сразу, а не пачкой в конце.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 С первой секунды сборки у ролика заведены пять этапов с оценкой времени; по ходу каждый переходит из ожидания в работу и в готово, оценка «осталось» уточняется, у готового записано, сколько он занял; при падении идущий этап помечен упавшим
- [x] #2 Отсев: на каждый отсеянный файл есть запись с решением «мимо» и причиной (смазан, экспозиция, не читается…); у этапа итог «годятся N из M»
- [x] #3 Разбор кадров: у файла с сохранённым описанием есть запись с меткой «что увидел» (описание и кто на кадре); у этапа итог «описано N из M»; описаний нет — этап проходит и честно говорит «0 из M»
- [x] #4 Режиссёрский этап без нейросети: по каждому файлу решение «беру» или «мимо» с причиной; серия одинаковых кадров — одной записью «взял 1 из N»; «включить» и «исключить» организатора видны в решениях
- [x] #5 Ритм и склейка: у этапа ритма запись, под какой трек и темп подогнаны куски; у склейки видно прогресс по кускам и итог — сколько склеек и какая длина
- [x] #6 Записи попадают в базу по мере появления, а не пачкой в конце этапа или сборки: тест читает журнал из другого соединения посреди сборки и видит уже написанное
- [x] #7 Повторная попытка того же ролика (повтор задачи или «повторить») начинает журнал с чистого листа; сбой записи журнала не роняет сборку
- [x] #8 Автотесты воркера на записанных ответах зелёные, в сеть и в базу человека не ходили; README воркера описывает, что и когда пишется в журнал

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Final Summary (coder, 2026-09-21). Журнал монтажа пишет оркестратор (montage.py) по тому, что вернули модули; новый journal.py — тонкий писатель по контракту api (миграция 130), схему не трогали. Отсев/режиссёр/ритм/сборка о журнале не знают.

ЧТО И КОГДА ПИШЕТСЯ. begin — сразу после чтения материала, до первого скачанного байта: пять этапов (screening, understanding, directing, rhythm, assembly) в pending с оценкой времени; повтор ролика стирает реплики и возвращает этапы в ожидание (чистый лист). Дальше по ходу: screening — start(total=файлы), запись decision=skip + reason (unreadable/blur/exposure) на каждый отсеянный, progress по каждому файлу, finish{kept, of, reasons}. understanding — читает готовые media_understandings (ничего не спрашивает у модели): на каждый описанный файл запись thought=описание + labels=cast_labels, finish{described, of, people, animals}; описаний нет — честное 0 из M. directing (путь без нейросети) — на каждый файл decision=take/skip; у take видео стоят source_from_seconds/source_to_seconds (кусок исходника, после stretch), серия — одной записью с series_size (взял 1 из N, размер ставит сам selection._dedup, дубли своих записей не получают); reason=excluded на вычеркнутом, reason=included на том, что организатор велел взять; finish{frames, of}. rhythm — finish{track (список треков заказа в порядке проигрывания), bpm (rhythm.tempo по тем же битам), cuts (сколько кусков сдвинулось)}; без музыки track=[] и cuts=0 — честное дорожки нет. assembly — start(total=куски), progress по каждому готовому нормализованному куску (assembly.assemble получил необязательный on_clip), finish{cuts, seconds} после того, как ролик лёг в хранилище. Падение: montage.give_up помечает failed тот этап, который шёл (там же, где упавшим называют сам ролик, — ролику с оставшимися попытками этап честнее оставить идущим).

РУЧКА ОЦЕНКИ ВРЕМЕНИ — journal.ESTIMATE, пара чисел на этап (секунд на файл, секунд на секунду готового ролика). Сумма по пяти этапам равна тому, чем api обещает соберём за N минут (estimateMinutes, TASK-197): 3 с на кадр и 1,5 с на секунду ролика; 214 кадров на 2:30 = 15 минут у обоих, пинится тестом test_the_worker_and_the_api_promise_the_same_minutes. Оценка идущего этапа пересчитывается по факту (потраченное время на сделанное), у закрытого — ноль, сколько занял считается по started_at/finished_at.

ЖИВОСТЬ. Каждая запись — отдельной командой на соединении воркера (autocommit), никакой транзакции вокруг сборки; порции маленькие — запись на отсеянный файл, одно UPDATE на готовый кусок. Тест читает журнал из ДРУГОГО соединения посреди сборки: видит записи отсева и режиссёра при status=processing и прогресс склейки 1,2,3,4 по кускам.

ЦЕНА ОШИБКИ. Всё, что пишет журнал, ошибку проглатывает и оставляет строку в логе (journal.quiet) — сборка идёт дальше, как и с раскладкой кадров.

МЕСТО ДЛЯ TASK-202: journal.entry принимает весь набор колонок контракта (thought, story_part, story_part_title, focus_x/y/w/h, labels); в montage.py путь с нейросетью помечен комментарием там, где пишутся решения отсева. ai.py и разбор плана не трогались.

ТЕСТЫ: новый test_journal.py (12 проверок, в том числе второе соединение), плюс rhythm.tempo в test_rhythm.py и series_size в test_selection.py. Весь набор зелёный — 192 после подтянутого main, в своей базе remember_m27_test и своём бакете remember-m27-test-201 (оба удалены), AI_PROVIDER сброшен, в сеть не ходили.

README воркера: новый раздел Журнал монтажа — что и когда пишется (таблица по этапам, оценка времени, живость, повтор, падение), journal.py в таблице файлов, абзац о втором соединении в Тестах.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Область: только projects/montage — montage/media/screening.py (job media_screening), возможно montage/sweeps.py
(если нужен отдельный триггер пересчёта, а не только «новый файл дошёл»). Ждать смёрженную TASK-447 (её
усиленная visual+time серия-дедуп — та самая логика, которой считать группы здесь) — работать поверх её кода.

Факт проверен заранее (лидом): api и mobile НИЧЕГО менять не нужно. screening_reason в БД — обычный text без
CHECK (миграция 060 намеренно без него), api отдаёт колонку как есть (src/media/gallery.ts), а в мобильном коде
'duplicate' уже полноправная причина (projects/mobile/src/lib/montage/order.ts — REASONS уже включает
'duplicate', с комментарием в коде: «the day the api does send it, an unknown word must not read as other» —
экран и тайл «Дубль» уже рисуют её). Общая галерея эти колонки вообще не читает (grep подтвердил — только
order.ts/gallery.ts на стороне api и order.ts на стороне mobile) — АС#5 уже сегодня выполняется архитектурой,
задача — не сломать это регрессией, тестом закрепить, что не сломано.

Что реально нужно (единственная недостающая часть): media_screening сегодня смотрит на ОДИН файл в изоляции
(judge() на нём одном) и никогда не пишет screening_reason='duplicate' — сравнение с соседями сознательно
вынесено в момент заказа (docs/jobs/screening.md). Chief подтвердил: хочет именно пересчёт «при подготовке
заказа», то есть по всему текущему готовому материалу воспоминания, полным честным пересчётом каждый раз, а не
разовой меткой.

Подход:
- После того как media_screening разобрала свой файл (как сегодня — unreadable/blur/exposure по нему одному),
  ДОПОЛНИТЕЛЬНО пересчитай серии-дубли по ВСЕМ уже разобранным (screening_reason не null) готовым файлам этой
  памяти — тем же _dedup() из TASK-447 (переиспользуй, не копируй логику). Пиши screening_rejected=true,
  screening_reason='duplicate' на проигравших внутри своей серии; на том, что раньше было отмечено дублем, а
  после пересчёта таким быть перестало (пришёл ещё кадр, серия распалась/изменилась) — верни исходный вердикт
  по этому файлу самому (unreadable/blur/exposure/чисто), а не оставляй 'duplicate' висеть.
  На памяти в 20-30 кадров это дёшево — пересчитывать целиком, не городить инкрементальный алгоритм (YAGNI:
  целевой случай — маленькое воспоминание, не архив на тысячи).
- НЕ трогай blur/exposure/unreadable вердикт файла, который дубль не проиграл, — оверрайд только на
  «выживших/проигравших» серии, остальные поля/причины как были.
- Только среди kind='ready', не hidden — как и сегодняшний отсев; исключённые организатором из УЖЕ поданных
  заказов эту колонку не трогают вовсе (worker судит заново на заказе, см. docs комментарий в api
  materialLeft — «The worker does not read the stored verdict»), эта колонка чисто витринная подсказка.
- Проверь тестом АС#3 буквально так, как формулировал chief: НЕТ персистентного «ручного оверрайда» в
  media_items — «возврат» кадра организатором живёт только в клиентском состоянии текущего заказа
  (include_media_ids на конкретном montages.params), сервер о нём не знает и никогда не знал (grep подтвердил
  — ни одной ручки записи screening_rejected в api, кроме самого воркера). Значит пересчёту здесь нечего
  затирать по построению — тест должен это и доказывать: пересчёт детерминирован по текущему состоянию
  материала и не зависит от истории прошлых пересчётов (два подряд запуска без изменения материала — одинаковый
  результат; смена состава серии — предсказуемо меняет вердикт, без остатков старого). Если при разработке
  найдёшь, что мобильный клиент всё-таки как-то персистентно хранит «возврат» на сервере (не должен, но
  перепроверь） — останови и доложи лиду, это меняет вывод.

Тесты: расширить существующий набор для media_screening (смотри tests/ по этой задаче job'а — docs/jobs/screening.md
и его тестовый файл), плюс модульный тест на сам пересчёт по нескольким файлам памяти. Golden journal-снимок эта
задача не трогает (screening — не журнал монтажа).

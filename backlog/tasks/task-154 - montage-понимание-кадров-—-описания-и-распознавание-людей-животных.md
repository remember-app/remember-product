## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
doc-03 / decision-9: нейросеть описывает содержимое каждого фото и видео воспоминания и узнаёт, что на разных кадрах один и тот же человек или животное («человек-1 — Лена, человек-2 — Сергей, животное-1 — Барсик»). Результат — вход для режиссёра (следующая задача) и должен переиспользоваться: второй и следующие ролики из тех же медиа не описывают уже описанные кадры заново (doc-03, Done when).

Как узнавать одних и тех же людей/животных на разных кадрах — решение исполнителя (человек прямо делегировал этот технический выбор). Один рабочий и достаточно простой путь: держать по каждому воспоминанию список уже узнанных действующих лиц («состав») и передавать его нейросети при разборе каждого следующего кадра того же воспоминания, чтобы она либо узнала уже известного, либо завела нового, — тогда сопоставление делает сама модель, а не отдельная своя система распознавания. Условие приёмки — не конкретный механизм, а результат: два кадра одного воспоминания с одним и тем же человеком получают одну и ту же метку.

Живых вызовов нет (decision-10 открыт, ключа нет) — пайплайн строится и проверяется на записанных ответах через шлюз из TASK-151.

Настоящее распознавание лиц живых людей не включать увереннее, чем позволяет decision-9: согласие даётся при регистрации (веха M-22, ещё не готова) — эта задача не блокируется её готовностью, но код не должен требовать включённого распознавания раньше, чем такая настройка появится.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Ветка: task-154-media-understanding в сабмодуле projects/montage, коммит 7953d48 (слияние в main — за лидом).

Что сделано:
- understanding.py — новый модуль пайплайна («понимание» из doc-03) и обработчик media_understanding: один готовый медиа-файл, одно описание. Зарегистрирован в worker.HANDLERS.
- schema.sql — новая таблица media_understandings: media_id (PK, id media_items текстом, как jobs.ref), memory_id, description, cast_labels text[], created_at. Без FK на media_items, по той же причине, что и у ai_requests: schema.sql должен накатываться на базу, где миграций API ещё нет. Строка пишется один раз и не обновляется.
- Задачу ставит media.media_preview концом успешной обработки (медиа стало ready) — прямой вставкой в jobs, потому что worker импортирует media, а не наоборот.
- worker.sweep_media_without_understanding — часовая докатка по образцу sweep_photos_without_previews (не дублирует идущую, упавшую трижды пробует через CATCH_UP_AFTER_HOURS). Первой строкой — выход, если поставщик не настроен: иначе каждый час в очередь уезжала бы вся библиотека ради ответа «некого спрашивать».
- README: раздел «Понимание кадров (media_understanding)» — таблица, механизм меток, что уходит в модель, поведение без ключа.

Решения исполнителя (развилки):
1. Устойчивость меток — через cast из TASK-151: перед каждым следующим кадром воспоминания собирается DISTINCT unnest(cast_labels) по memory_id и уходит в запрос. Своей системы распознавания нет, сопоставление делает модель (decision-9). Поэтому задача на один файл, а не на воспоминание: состав растёт по кадру за раз.
2. В модель уходят не оригиналы, а копии от media_preview: фото — крупной копией (preview_key), видео — FRAMES_PER_CLIP=3 кадрами, вырезанными из 720p-превью равномерно и не с краёв. Кадрами, а не клипом целиком: OpenAI видео не принимает вовсе, Gemini считает клип по длине (258 ток./сек, doc-11). Потеря движения помечена ponytail-комментарием в understanding.py с путём апгрейда.
3. Без поставщика (сегодня) обработчик выходит до скачивания и до шлюза — не пишется даже строка skipped в ai_requests. Иначе журнал каждый час набивался бы пустыми строками по всей библиотеке. Строка «нет модели» остаётся в логе.
4. Ответ без description считается провалом вызова (raise → обычные повторы), чтобы пустое описание не легло в таблицу навсегда и не ушло режиссёру.

Тесты: test_understanding.py, 7 штук, сеть не трогают — модель отвечает записанными файлами (fixtures/gemini_describe.json и новый gemini_describe_again.json: модель узнаёт человек-1 и заводит человек-2). Фикстуры базы/бакета переиспользованы из test_media.py, транспорт — по образцу test_ai.py. Полный прогон: 83 passed (было 76) на живых Postgres/MinIO/ffmpeg.

Осталось за рамками (для TASK-156): montage.py описания пока не читает — режиссёр сам решит, ждать ли неописанные кадры при заказе ролика; и уборки осиротевших строк media_understandings после удаления медиа нет — как и у ai_requests.

## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Сервер хранит журнал монтажа вместе с роликом и отдаёт его приложению по мере того, как он пишется: пять этапов с оценкой времени, записи журнала, кто сейчас смотрит. Читает любой участник воспоминания — и во время сборки, и после неё, сколько бы времени ни прошло.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Миграция заводит хранилище журнала: записи (этап, файл, мысль, решение «беру»/«мимо», причина, «взял 1 из N», часть истории, кусок исходника, метки «что увидел», рамка «куда смотрит»), пять этапов у каждого ролика (состояние, оценка времени, счётчики, итоги) и зрителей. - [x] #2 Один маршрут чтения по ролику отдаёт: состояние ролика, пять этапов (состояние, оценка, счётчики «взял / мимо / мысли», итоги), записи порциями от курсора (можно сузить до одного этапа или одного файла), тех, кто смотрит сейчас, и сведения о файлах из записей — тип, кто принёс, когда снят, ссылка на миниатюру; файла уже нет — запись без сведений, не ошибка
- [x] #3 Читает любой участник воспоминания, включая зрителя; посторонний и несуществующий ролик получают один и тот же 404, как везде

- [x] #6 Контракт — таблицы, колонки, значения этапов, решений и причин, форма ответа, кто что пишет — описан в README api: по нему воркер будет писать, а приложение читать
- [x] #7 Автотесты на права (участник, зритель, посторонний), порции по курсору, отметку зрителя, удаление ролика и кадра, пустой журнал зелёные; линт и типы api зелёные; тесты шли в своей базе, не в живой

ЭТАПЫ, по порядку, ключи: screening «Отсев брака», understanding «Разбираем, что на кадрах», directing «Режиссёр строит историю», rhythm «Раскладываем в ритм трека», assembly «Склеиваем». Названия этапов и слова причин показывает приложение на своём языке — в базе коды, не фразы.

ЗАПИСЬ ЖУРНАЛА (только дописывается; курсор — возрастающий id): этап; файл (id медиа, может быть пустым — «мысль про план в целом»; БЕЗ внешнего ключа — запись переживает удаление кадра и ухода участника); мысль (текст модели, может быть пустой); решение «беру» / «мимо» / нет решения (чистая мысль); причина отказа кодом (blur, exposure, unreadable, duplicate, excluded, no_room, …); «взял 1 из N» — размер серии; часть истории (номер и название); кусок исходника, который взят (от / до, секунды); метки «что увидел» (список строк); рамка «куда смотрит» (доли 0..1: x, y, w, h — может быть пустой); время записи.

ЭТАП (по строке на этап на ролик, пять штук, воркер их обновляет): состояние (ожидает / идёт / готов / упал), когда начался и закончился, оценка времени в секундах (для идущего — сколько осталось), счётчики сделано / всего, итоги этапа свободным jsonb (что в нём лежит — описать в README на каждый этап: «212 из 214 годятся», «37 лиц» и т.п. приложение форматирует само). Счётчики «взял N / мимо N / мысли N» по этапу считает api из записей.

ЗРИТЕЛИ: (ролик, пользователь, когда спрашивал последний раз); окно «сейчас смотрит» — константа в config (порядка 20 секунд); в ответе id и ник.

Место кадра в ролике (секунда начала, длительность) здесь НЕ хранится: его записывает воркер в общую таблицу раскладки, которую заводит TASK-191 (веха Afisha 2). Отдельная задача после слияния TASK-191 присоединит его к сведениям о файле — здесь оставить под это место в ответе, ничего не выдумывая.

ОТВЕТ должен помещаться в один полл приложения раз в секунду-две: записи порциями (лимит по умолчанию порядка 200, has_more), сведения о файлах только для тех, что встретились в порции, ссылки на миниатюры подписаны как в галерее.

Миграция: номер ВЫШЕ самого большого на main api на момент слияния — сегодня это 090, но вехи Labels, Montage order и Afisha 2 тоже заводят миграции: проверить main перед стартом и ещё раз перед слиянием, никогда не встраивать между существующими (на этом уже дважды спотыкались). ## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Журнал монтажа лежит вместе с роликом и читается одним маршрутом.

МИГРАЦИЯ 130.do.montage-journal.sql (+ undo). Номер взят выше самого большого на main (100, frame-info) и выше заявленных 110 и 120. Три таблицы, все на montages(id) ON DELETE CASCADE — ушёл ролик или воспоминание, журнал ушёл с ним:

- montage_journal_entries: id (bigserial, он же курсор), montage_id, stage, media_id (БЕЗ внешнего ключа — запись переживает удаление кадра и уход участника), thought (<=500), decision (take|skip|null, CHECK), reason (код воркера, <=40, без CHECK), series_size, story_part, story_part_title (<=80), source_from_seconds, source_to_seconds, labels (text[], <=12 шт и <=240 символов всего), focus_x/y/w/h (доли 0..1, CHECK «все четыре или ни одной»), created_at. Индекс (montage_id, id).
- montage_stages: PK (montage_id, stage), state (pending|running|done|failed), started_at, finished_at, eta_seconds, done_count, total_count, outcome jsonb. Воркер кладёт через ON CONFLICT DO UPDATE.
- montage_viewers: PK (montage_id, user_id), last_seen_at. Единственная таблица, в которую пишет api.

ЭТАПЫ (коды): screening, understanding, directing, rhythm, assembly.

МАРШРУТ: GET /memories/:memoryId/montages/:montageId/journal, за app.authenticate + app.requireMembership (читает любой участник, зритель тоже; посторонний и несуществующий — один 404). Параметры: after, before, limit (200, потолок 500), stage, media_id. Ответ: { montage {id,status}, stages[] (со счётчиками taken_count/skipped_count/thought_count, которые api считает по записям), entries[] (свежие сверху, четыре доли рамки собраны в focus), has_more, files[] (только файлы отданной порции: kind, uploaded_by, captured_at, duration_seconds, подписанная thumbnail_url), viewers[] (id, username) }.

Пока ролик queued или processing, сам запрос читающего — один upsert — отмечает его смотрящим; у ready и failed не отмечает никого. Окно — MONTAGE_VIEWER_WINDOW_SECONDS (20). Ролик без журнала отвечает пустым ответом, а не ошибкой.

Место кадра в ролике сюда не клалось: оно в montage_frames (TASK-191), присоединит его отдельная задача — в README это записано.

README api: раздел «Журнал монтажа — как это устроено» (таблицы, ключи outcome на каждый этап, потолки), описание маршрута, рекомендованная частота опроса 1–2 секунды, строка MONTAGE_VIEWER_WINDOW_SECONDS в таблице окружения, строка журнала в контракте с воркером.

ПРОВЕРЕНО: src/montages/journal.test.ts — 7 тестов (права участник/зритель/посторонний, порядок этапов и счётчики, порции по курсору в обе стороны и сужения, полная запись со сведениями о файле и подписью миниатюры, отметка смотрящего на queued/processing против ready/failed, пустой журнал, удаление кадра и ролика). Весь пакет: 114 тестов, 12 файлов — зелёные; линт и типы зелёные. Гонялось в своей базе remember_m27_test и своём бакете, живую базу remember не трогало; база и бакет удалены.
